Why I stopped trusting my own code reviews

A look at the review habits that felt thorough but were quietly missing the same category of bug, every time.

PublishedMarch 2026
Read time6 min
CategoryEngineering

For a couple of years I thought I was a careful reviewer. I read every diff top to bottom, left comments on naming, and caught the occasional off-by-one before it shipped. Then a production incident traced back to a pull request I had personally approved, twice, and I went looking for the pattern instead of just fixing the bug.

The pattern wasn't hard to find once I looked. Almost every miss I could remember was the same shape: the code did exactly what the diff showed, and the diff showed exactly what the author intended — the bug lived in what the change didn't do. A missing rollback path. A cache that never got invalidated. An edge case that only existed once two other systems changed at the same time.

Reading the diff instead of the change

A diff is a proposal about the parts of the system that changed. It says nothing about the parts that should have changed and didn't. I was very good at judging the code in front of me and never developed a habit of asking what else this touches that isn't here.

The bugs that got past me weren't hiding in the code. They were hiding in what the code assumed about everything around it.

So I changed the question I ask first. Instead of "is this correct," I now start with "what does this assume is true elsewhere, and is it." That single reframe has caught more real issues in the last few months than any amount of careful line-by-line reading did before it.

What actually changed in practice

  • I trace one level up the call graph before approving anything that touches shared state.
  • I ask the author to name the assumption out loud in the PR description, not just describe the change.
  • I stopped treating "looks clean" as a proxy for "is correct" — they're unrelated most of the time.

None of this makes reviews faster. It makes them slower, in fact, and that's fine. The goal was never speed — it was catching the bug that a clean diff is specifically good at hiding.
