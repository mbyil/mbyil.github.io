A field guide to reading other people's systems

Notes on getting oriented in an unfamiliar codebase quickly, without waiting for someone to explain it to you.

PublishedSeptember 2025
Read time7 min
CategoryEngineering

Every new job starts the same way: an unfamiliar codebase, no map, and a growing sense that everyone else already understands how it fits together. Over a few of these transitions I've landed on a routine that gets me oriented faster than reading the code start to finish ever did.

Start at the edges, not the center

The instinct is to open the biggest, most important-looking file and start reading. That's usually the wrong place to start — it's dense, it assumes context you don't have yet, and it won't tell you how data gets there in the first place. I start at the edges instead: where does a request enter the system, and where does data leave it. Those two boundaries tell you more about the shape of a system than its core logic does.

Follow one real request, end to end

Pick the most common thing a user does, and trace it through the system by hand — not by reading, by actually running it with logging or a debugger attached. This does more for orientation in an hour than a week of passive reading, because it forces you to see the real path instead of the path the folder structure implies.

Architecture diagrams show you what the system is supposed to do. Tracing a real request shows you what it actually does.

Ask what would break it

Once I can trace the happy path, I try to guess the failure modes before I look them up — what happens if this call times out, what happens if this queue backs up. Being wrong is fine and often more informative than being right, because someone correcting you tends to explain the actual constraint, not just confirm the guess.

A short list, in order

  • Find where requests enter and where data leaves.
  • Trace one common request end to end, by running it.
  • Guess the failure modes, then check.
  • Only then read the core logic — now you have context for it.

None of this is exotic. It's mostly a discipline of resisting the urge to read code passively when tracing it actively teaches you more, faster.
